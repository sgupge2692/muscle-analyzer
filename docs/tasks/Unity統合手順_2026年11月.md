# Unity統合の技術検証手順（トラックB フェーズ3・2026年11月13日）

トラックBフェーズ1（R3Fメッシュ人型）が完了した（`frontend/src/components/AvatarViewer3DR3F.tsx`）。本ドキュメントは，Unity を導入するかどうかの意思決定と，導入する場合の手順を整理するものである。

**前提の原則**: 計画書の「フェーズ3：要再検討」のとおり，**Three.js で目的が達成できるなら Unity は導入しない**判断がデフォルト。Unity 導入は，「Three.js では実現できない明確な要件」が発生した場合に限る。

---

## 1. 先に見極めるべき要件の有無

Unity を検討する理由が以下のいずれにも該当しなければ，案A（Three.js継続）で確定させる。

| 候補要件 | Three.js で代替できるか | 備考 |
|---|---|---|
| 高品質なスキニングメッシュのリアルタイム変形 | できる（GLB + SkinnedMesh / mixamo アニメをランドマークでブレンド） | R3F で `<useGLTF>` + `mixamo` リターゲットが定番 |
| 物理シミュレーション（筋骨格モデル・慣性） | 部分的に可能（自前実装が必要） | 本命は筋骨格モデル系（OpenSim等）であり Unity 物理（PhysX）は筋活動推定に直接寄与しない |
| PBR・ライティングの高品質化 | できる（three.js の標準機能） | |
| VR/AR展開 | できる（WebXR / three.js） | |
| コンソール品質のレンダリング | 難しい | 要件として本当に必要かは疑問 |

**結論の目安**: 卒論スコープでは物理シミュレーション（筋骨格モデル）を実装しないため，Unity 導入の動機は存在しない。ケーススタディとして検証手順だけ確定させておく（以下）。

---

## 2. 案A（推奨・デフォルト）: Three.js の完成度を上げる

1. **リグの品質向上**: 現行のカプセル人型を，GLB スケルトン（Riggedモデル）に差し替える
   - モデル調達: mixamo（無料・利用規約確認）またはオープンな rigged GLB（CC0）
   - 実装: ランドマーク→ボーンの回転解決（骨の長さはモデル側に合わせ，ランドマークの関節位置からIK的に姿勢を決める）
2. **筋活動の熱表示をメッシュ頂点色/マテリアルで表現**（既存はボーン単位の発光。頂点単位にすると筋の形が見える）
3. **パフォーマンス**: 30fps × 20ボーンは余裕。InstancedMesh は不要

工数目安: 2〜4週間（週末ペース）。Unity より小さく，配信負荷も軽い。

---

## 3. 案B: Unity WebGL 組込み（比較検証用の手順）

### 3.1 技術スタック

- Unity 2022 LTS 以上（WebGL ビルド）
- フロント埋め込み: `react-unity-webgl`（npm）
- データ入力: バックエンド `/analyze` の `landmarks_3d`（MediaPipe world座標の時系列 JSON）を Unity 側の C# パーサで読み，人型リグに適用

### 3.2 手順

1. Unity プロジェクト新規作成（WebGL テンプレート）
   - 環境: macOS では Universal Windows/WebGL ビルドサポートを確認
   - 人型リグ: mixamo から rigged モデルを FBX で取り込み
2. C# 側: `LandmarkPlayer` クラス
   - `SetFrame(int index, float[] landmarks)` を public にし，`DllImport("__Internal")` な JS→Unity ブリッジ（`SendMessage`）を受ける
   - 17〜33関節 × xyz の配列 → Animator の Humanoid Rig に合わせた回転に変換（親ボーンからの相対回転を計算）
3. ビルド: Unity WebGL ビルド（gzip/brotli 圧縮を有効化）
4. React 側:
   ```bash
   npm install react-unity-webgl
   ```
   ```tsx
   const { unityProvider } = useUnityContext({
     loaderUrl: "/unity/build.loader.js",
     dataUrl: "/unity/build.data.br",
     frameworkUrl: "/unity/build.framework.br",
     codeUrl: "/unity/build.wasm.br",
   });
   <Unity unityProvider={unityProvider} />;
   // フレーム送信
   sendMessage("LandmarkPlayer", "SetFrame", JSON.stringify(frame));
   ```
5. 配信: ビルド成果物（数十MB）を `frontend/public/unity/` に置くと Vercel のデプロイサイズ・ロード時間が大幅増。S3/R2 + CDN 置き（遅延ロード）が現実的

### 3.3 Unity WebGL の制約（導入判断に直結）

- **初期ロード 20〜50MB**: モバイル回線で数十秒。筋トレアプリの利用文脈（撮影→すぐ結果）と相性が悪い
- **iOS Safari**: WebGL は動作するがメモリ制約が厳しい（1GB超のヒープでクラッシュしやすい）
- **ライセンス**: Unity Personal は年間売上条件あり（2026年時点の規約を要確認）
- **本番データフロー**: R3F 版と違い，JSON→WASM ヒープへのコピーがフレームごとに発生（最適化必須）

### 3.4 検証ポイント（もしやるなら1日で見極められる）

- 空の Unity WebGL ビルドを Vercel 置きでロードし，iOS Safari + Android Chrome で初期ロード時間を測定
- `SendMessage` で 30fps のランドマーク送信が追従するか（フレームドロップ率）
- 上記が満たされない場合，案Aへ確定

## 4. 案C: Unity を使わないネイティブiOS（参考）

「iOSアプリとしての存在」（競合調査第4節の区別）を本当の意味で達成するなら，WebGL よりネイティブの選択肢がある。

- **SwiftUI + ARKit/SceneKit**: MediaPipe iOS ライブラリ or Apple Vision（VNDetectHumanBodyPose3D）で骨格→ SceneKit のスキニング人型に適用
- トレーニング済み 1D-CNN の iOS 端末実行は Core ML 変換が定石（torch 2.x → coremltools）
- 工数は大きいが，「出荷済みiOSアプリ」の新規性主張（4条件の合取）に直結する唯一のレーン

## 5. 判断マトリクス（現時点）

| 評価軸 | 案A: Three.js継続 | 案B: Unity WebGL | 案C: ネイティブiOS |
|---|---|---|---|
| 工数 | 小 | 大 | 大 |
| ロード時間 | 秒単位 | 数十秒 | インストール後即 |
| 卒論への貢献 | 課題Cの可視化に十分 | 貢献ほぼゼロ（スコープ外） | なし（卒業後） |
| 市場化後の伸び | Webで十分 | 特化した高度可視化 | 新規性主張の直接達成 |

**現時点の推奨**: 案Aを完成させ，案B/Cは「実施しない」と明示的に記録しておく（実施しない判断も技術検証の成果物として計画書の将来展望に書ける）。
