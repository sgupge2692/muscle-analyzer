## S1. `/analyze` の認証必須化＋利用枠

**現状**: `main.py:210` — `credentials = Depends(security)` のオプション認証。無効トークンは無視される（`main.py:220-227`）。IP単位 `10/minute` のレートリミットはあるが，アカウント不要で使える。

**設計案**:

- 認証: `Depends(get_current_user)`（`auth.py:366`）に置き換え，未認証を 401 にする
- 研究デモ用の無認証運用は ENV で分岐（`ENV=development` のときのみオプション認証を許可）。本番は常に必須
- 利用枠（プラン連動）:
  - `users` テーブル（Supabase）に `plan`（free / paid）と `usage_month`（年月）を追加
  - `plan_limits = {free: 3, paid: 30}`（**枠数は要確認** — フリーミアム境界はマーケ検討と連動。本メモでは仮値に留める）
  - `/analyze` 冒頭で当月実行数をカウントし，枠超過は 402/429 を返す。カウント方法は (i) users テーブルのカウンタ列を原子的インクリメント，(ii) 解析履歴テーブルのレコード数を数える，の2案 → (ii) が履歴機能（commercialブランチ実装済み）と整合するので仮採用
  - 失敗した解析（検出不能等）はカウントから除外するかを要確認（保守的には除外＝ユーザーに有利な側）
- レートリミットは IP 単位の S4 と併存させる（認証済みでも短期の爆発的連打は止める）

## S2. リフレッシュトークン機構

**現状**: `auth.py:440` — `/refresh` は有効なアクセストークンを持つユーザーに新トークンを発行するだけ。失効・ローテーションはなし。

**設計案**:

- トークン構成: access（15分）＋ refresh（30日，JWT ではなく不透明トークン＋サーバー側ハッシュ保存）を想定。access を短くするほど失効に強い
- refresh の保存先: users.json モードではメモリ/ファイルに `refresh_tokens: {hash: {user_id, expires_at, rotated_from}}`。Supabase モードでは専用テーブル `refresh_tokens`
- **ローテーション**: `/auth/refresh` は旧 refresh を無効化し新 refresh を発行。**使用済み（rotated_from に一致する）トークンの再使用を検知したら，そのユーザーの全 refresh を失効させる**（盗難検知の定石）
- 失効エンドポイント: `/auth/logout`（refresh を無効化）。access 自体はJWTなので自然失効まで有効が残る（15分は許容と仮採用）
- users.json モードは原子的置換書き込み（`auth.py:198`）を踏襲する

## S3. トークン保管の HttpOnly Cookie 化

**現状**: `frontend/src/lib/api.ts:151` — localStorage に JWT。XSS で盗める。

**設計案**:

- refresh トークンは **HttpOnly + Secure + SameSite=Lax + Path=/auth** の Cookie で配布。JS から読めないので XSS で refresh を盗めない
- access トークンも HttpOnly Cookie（SameSite=Lax）にし，フロントは Authorization ヘッダーを使わない設計に移行
- CSRF 対策: SameSite=Lax で大部分は防げる。追加の保険として，backend 側 `Origin`/`Referer` チェック（WebSocket で既に自前実装がある `main.py:77` と同様の方式）を仮採用。CSRFトークンの二重実装は要確認（複雑さトレードオフ）
- WebSocket（`/ws/stream`）への認証: Cookie は WS ハンドシェイクに付くので Origin チェックと併せて Cookie 認証に寄せる
- 移行手順: (1) サーバーが Cookie と従来の Authorization ヘッダー両方を受ける移行期間 → (2) フロントを Cookie に切替 → (3) ヘッダー受付を廃止。長期移行期間を設けるのは既存ユーザーのセッションを切らないため
- CSP は Vercel 側ヘッダー（S9）とセットで設定

## S4. レートリミットの Redis 移行

**現状**: `auth.py:353` — メモリ内（プロセス単位）。workers 2 で非共有，X-Forwarded-For 依存。

**設計案**:

- Railway Redis アドオンを追加し，トークンバケット or 固定窓カウンタを Redis で共有実装に置換
- キー: `rl:{endpoint}:{ip or user_id}`。認証済みエンドポイント（S1適用後）は **user_id ベース**，未認証は IP ベース
- X-Forwarded-For の信頼問題: Railway のプロキシが付与するヘッダのみ信頼する（信頼済みプロキシの固定）→ 詳細は実装時に Railway 側仕様を確認（**要確認**）
- フォールバック: Redis 到達不能時は現状のメモリ内制限に degrade する（サービス全体を止めない）。main.py の rate_limit_handler（`main.py:131`）の構造を踏襲

## S5. パスワードリセット・メールアドレス検証

**現状**: 未実装（change-password は現行パスワード確認ありのみ，`auth.py:470`）。

**設計案**:

- メール送信: Resend（シンプルなREST API）or AWS SES。**依存追加は実装時に承認を取る**（新規pipパッケージの原則）
- フロー（リセット）:
  1. `/auth/request-reset`（レートリミット必須，メール存在有無に関わらず同じ応答を返す＝アカウント列挙対策）
  2. 不透明トークン（ワンタイム・30分失効・ハッシュ保存）を生成し，署名付きリンクをメール送信
  3. `/auth/reset-confirm` でトークン検証＋新パスワード設定（バリデータは既存の `validate_new_password` を再利用）
  4. 使用済みトークンは即無効化。**リセット成功時は該当ユーザーの全 refresh セッションを失効**（S2 と連動）
- メールアドレス検証: 登録時に検証トークン発行 → 検証完了まで解析履歴保存等の一部機能を制限するかどうかは要確認（保守的には制限しない＝spam防止に留める）
- users.json モードとの整合: メール関連は Supabase モードを前提に設計し，users.json モードでは機能を無効化する（開発環境でメール送信しない）

1. S2（refresh トークン）— S3/S5 の前提になるため最優先
