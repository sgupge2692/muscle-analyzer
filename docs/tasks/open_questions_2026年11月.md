# Open Questions（2026年11月・自走タスク用）

`docs/tasks/opencode_自走指示_2026年11月.md` の自走中に判断に迷った箇所の記録。各項目に選択肢・仮採用した案・理由を記載する。数値・パラメータは GUARDRAILS 通り根拠のない値を埋めず、設計判断は保守的な方を仮採用した。

## Q1. Deadlift/Quadriceps の低整合（r=0.685）に対する対処

- **状況**: Moreira et al. 2023 の data_points 追加後の検証で r=0.685（低整合）。文献はミッドプル(126°)とロックアウト(180°)の RF が有意差なし（40.50 vs 46.85, p=0.998）なのに対し、対称ガウス（peak=95, width=35）はロックアウト側を大きく減衰させる。
- **選択肢**:
  1. 現状維持・限界として記録する
  2. width を広げて再指定する（r は向上するはず）
  3. Squats と同様に独立文献・解剖学的根拠が得られた時点で再較正する
- **仮採用**: 1（現状維持・限界記録）
- **理由**: width の調整は検証データ（3点）に合うようパラメータを見直すことになり、検証データからの逆算禁止ルール（自走指示タスク3・GUARDRAILS の過学習防止）に抵触する。r=0.685 は「事前指定パラメータに対する整合確認」の結果として報告するのが誠実。改善する場合は 3（独立根拠の確保）が前提。

## Q2. Moreira et al. 2023（等尺性最大牽引）を Deadlift の角度別文献値として採用することの妥当性

- **状況**: Deadlift の角度別定量値を持つ唯一の公開文献が等尺性条件（動的12RM ではない）。Escamilla et al. 2002 の動的データは Table 1 に角度区間別値があるが全文要購読で数値転記不可。
- **選択肢**:
  1. 採用する（条件差は note で明記）
  2. 採用せず検証不可のままにする
  3. Escamilla 2002 の購読を入手して動的データでやり直す
- **仮採用**: 1（採用）
- **理由**: 角度位置パターンの定性傾向は Escamilla 2002 の本文記述と一致しており（四頭筋・脊柱起立筋は高屈曲側、ハムストは伸展側で大きい）、角度別定量値としては最良の公開情報。条件差（等尺性・最大努力・n=20）は data_points の unit/validation_note に明記した。研究計画書の「文献定量点の追加取得」要件を満たすには公開可能な定量値が必要という判断。Escamilla 2002 の購読入手は実装者（人間）の判断事項として残す。

## Q3. Deadlift/Hamstring の peak_angle_deg=150 の妥当性

- **状況**: 実測（Moreira et al. 2023）では BF のピークはミッドプル126°だが、検証データからの逆算は禁止のため peak には使えない。独立根拠として Escamilla et al. 2002 本文の「hamstring data were highest between 0 and 60°KA（0°=膝完全伸展）」＝解剖学的角度120–180°の区間があり、その中央値150°を事前指定した。結果として r=0.836（部分整合）。
- **選択肢**:
  1. 150°（Escamilla本文区間の中央値）を維持
  2. 126°（実測ピーク）に変更する → 逆算に該当するため非推奨
  3. peak=null にして Hamstring は変調なしにする
- **仮採用**: 1
- **理由**: 独立文献に基づく事前指定という設計ルールに最も忠実。実測ピーク(126°)との差は 24°であり、検証の r にその分の乖離が含まれるのは事前指定パラメータの整合確認としては正常な振る舞い。

## Q4. uvicorn に WebSocket ライブラリが入っていない問題（依存追加の提案・承認待ち）

- **状況**: 最終動作確認で `/ws/stream` の WS ハンドシェイクが失敗。原因は `requirements.txt` が `uvicorn==0.54.0`（extras なし）で、WebSocket 実装（websockets または wsproto）が依存に含まれないため。uvicorn が「No supported WebSocket library detected」を出力し `/ws/stream` が 404 になる。git 履歴でも websockets は requirements.txt に入ったことがない。**Docker 本番（Dockerfile も同一の uvicorn）でも WS トランスポートは同様に失敗する可能性が高い。** ※デプロイ設定・依存関係は GUARDRAILS で触れないため、変更はしていない。
- **選択肢**:
  1. `requirements.txt` の該当行を `uvicorn[standard]==0.54.0` に変更（websockets を含む extras）
  2. `websockets` を別行で追加
  3. 変更せず、WS の検証方法を別途検討する
- **仮採用**: なし（実施していない）。確認を要するため記録
- **理由**: 依存追加は承認事項（GUARDRAILS）。本来は WS リアルタイム解析の最終動作確認で WS 経由のフレーム送受信まで確認する予定だったが、トランスポート層が環境で使えないため、確認は「接続先エンドポイントの存在」「RealtimeAnalyzer（PoseLandmarker）生成」「rep_detector によるレップ検出」「/analyze での筋活動推定・evidence_levels 出力」までで代替した。WS 本体のコード（websocket_stream.py 等）は今回の変更対象外であり、1行も変更していない。
- **結果（解決済み）**: ユーザーの承認を得て `uvicorn[standard]==0.54.0` に変更（コミット 2ad2f60）。ローカルで WS ハンドシェイク＋ping/pong を確認済み。なお許可オリジン外クライアントへの 403 応答はエンドポイント自体の Origin チェックの正常動作であり、問題ではない。

## Q5. `scripts/evaluate_f1_comparison.py` がローカル venv で実行不可（torch なし）

- **状況**: 全テスト実行時に torch がローカル venv（`.venv`）に無く `ModuleNotFoundError`。ML 学習は venv 外・別環境で実行する運用（AGENTS.md）と整合しており、今回の変更（anatomy の文献カーブ・検証スクリプト）とは無関係の既存状態。
- **選択肢**:
  1. venv に torch を入れる（軽くない）
  2. 実行しない（F1 評価は学習環境で実施する既存運用を維持）
- **仮採用**: 2
- **理由**: 依存の追加・変更は承認事項であり、本タスクのスコープ（文献較正パイプライン）に F1 評価スクリプトの実行は必須ではない。実際に F1 micro 0.966 の事前実験値（研究計画書v17に記載）は既に取得済み。
